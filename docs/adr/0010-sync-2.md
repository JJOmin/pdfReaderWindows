# 10. Sync 2: automatic, selective, sent

Date: 2026-10-22

Status: **Accepted** by the owner on 2026-10-22 with the recommendations of choices 1, 2, 3 and
5: a sent document is asked for, with "Always accept from this computer"; QR pairing needs no
click; `qrcode-generator` and `mobile_scanner` are approved; sync with the phone app closed comes
later. Choice 4, the intervals, stays as written until the owner changes it. The steps are S10 to S17 in
SPEC.md and M7 in the Flutter repository's PLAN.md. It changes ADR 7 (Wi-Fi) and ADR 8 (the
store), and removes Dropbox from ADR 8.

## Context

The owner uses Nextcloud between the MacBook and the Android phone, and reads on both. Today:

- **Nothing syncs on its own.** The desktop sends to Nextcloud when "Sync now" is pressed or a
  document was just prepared. The phone fetches when its Sync button is pressed. A mark made on
  the laptop reaches the phone only after both pressed a button.
- **A sync walks the whole store.** Both sides list every document folder and read every place
  and notes file to learn whether anything changed. That grows with the library.
- **The phone shows two lists.** "Prepared on the desktop" on the home screen holds what is on the
  phone; the Cloud screen lists what is in Nextcloud. What is only in the cloud, what is on the
  phone, and what is out of date is not visible in one place.
- **Pairing over Wi-Fi means typing a 12-character code.**
- **The desktop cannot hand a document to the phone.** The phone has to go and fetch it.
- **Dropbox is built but not used.** It needs a registered app key the owner has not made, and it
  doubles the store code on both sides.

The owner's aim: switch from the laptop to the phone and find the changes there within a minute
with the app open, or at once after pulling to refresh; choose which documents are on the phone;
pair by scanning; and send a document from the laptop to the phone.

## Decision

### 1. Dropbox is removed for now

`main/sync/dropbox.ts`, its sign-in, its tests and fake server, and its button go; so do the
phone's `dropbox_store.dart` and its part of the Cloud screen. The store interface stays, so a
second service can come back. Git keeps the code (the commit is named in ADR 8).

### 2. A change journal: one cheap request says whether anything is new

Each device writes one small sealed file, `devices/<device>.json`, after every sync that sent
something:

```
{ "device": "…", "name": "Leos-MacBook", "updated": 1792658000000,
  "docs": { "<docId>": { "manifest": t, "notes": t, "state": t } } }
```

`t` is when that part last changed on that device. A reader lists `devices/` once (one WebDAV
PROPFIND, which returns each file's ETag) and opens only the journals whose ETag changed since it
last looked, then fetches only the documents and parts newer than what it has. A poll that finds
nothing new costs one request. Each device writes only its own journal, so no two devices write
the same file (the same rule as the places in ADR 8 section 4). The journal is a hint, not the
truth: "Refresh everything" still walks the whole store as today, and repairs anything a lost
journal missed.

### 3. Automatic sync with Nextcloud

- **Desktop.** Signed in, it syncs on start, 10 seconds after the last local change (a mark, a
  comment, a document prepared; the place in the document counts here too, at most once a
  minute), every 2 minutes for other devices' changes, and when the app quits. The sync button
  (MAC5) shows it, and "Sync now" stays.
- **Phone.** While the app is open, it polls the journals every 30 seconds, syncs 5 seconds after
  its own change, and syncs when the app comes to the front. Pull to refresh walks everything. An
  icon in the app bar shows the same four states as the desktop's button.
- **What gets synced is chosen per document**, as now: on the desktop with "Add this document"
  (renamed "Sync this document"), and the phone only downloads what the user downloaded before or
  accepted (section 6).
- Expected delay, app open on both: a mark made on the laptop is on the phone within about 40
  seconds (10 s to send, up to 30 s to be seen), at once after a pull to refresh.
- Not in this step: syncing while the phone app is closed. Android allows that only through
  WorkManager, at most every 15 minutes, which needs a package (owner's choice 5).

### 4. The phone's library: on the phone, in the cloud, or both

The home screen becomes one list of every document the phone knows, from Nextcloud and from paired
computers, each with its state:

- **On this phone** (up to date), **Update available**, **In the cloud** (not downloaded; tap to
  download), **Downloading 40 %**, **Offered by Leos-MacBook** (section 6).
- Filter chips: All, On this phone, Cloud only. A line at the top: "1.2 GB on this phone".
- Per document, from a long press or a menu: Download, Remove from this phone (it stays in the
  cloud), Open.
- Downloads the phone starts on its own (updates, accepted offers) wait for Wi-Fi; a tap always
  downloads. The phone asks Android whether the network is metered, through the existing platform
  channel; no package needed.
- The Cloud and Desktops screens move into one **Sync** screen: the Nextcloud account and key, the
  paired computers, and "Scan to pair".

### 5. Pairing by QR code

The desktop's Phone dialog shows a QR code next to the typed code. It holds
`pdfreader://pair?v=1&name=<computer>&addr=<ip:port,…>&code=<XXXX-XXXX-XXXX>&secret=<random>`:
the addresses, so the phone needs no multicast; the code, which pins the certificate exactly as
when it is typed (ADR 7 section 6); and a one-time secret, made when the dialog opens and dropped
when it closes. A phone that presents the secret proves it saw this screen just now, so the
desktop pairs it without the Accept click (owner's choice 2). Typing the code keeps working.

- Desktop: a QR encoder package (owner's choice 3).
- Phone: a camera scanner package (owner's choice 3), and the camera permission, asked only when
  "Scan to pair" is tapped.

### 6. Wi-Fi works like the cloud, and the desktop can send

- **Automatic over Wi-Fi.** While the phone app is open, it listens for the paired computers'
  announcements. When one is heard it syncs at once, then asks `GET /v1/changes?since=<t>` every 5
  seconds, the journal of section 2 served directly. The desktop's dialog shows each phone as
  "connected, synced 12:03".
- **Sending.** A document on the desktop gets **Send to phone**, in the sync button's menu and the
  dialog. It prepares the document if it is not prepared yet, then puts it in that phone's inbox:
  `GET /v1/inbox` over Wi-Fi, or `inbox/<phone device>.json` in the store when the phone is away.
  The phone shows **"Leos-MacBook sends paper.pdf (12 MB): Accept, Decline"**, and downloads it
  after Accept (owner's choice 1). A declined document leaves the inbox. A sent document is synced
  from then on, as if the phone had downloaded it.

## Consequences

- New Wi-Fi requests (`/v1/changes`, `/v1/inbox`, pairing with a secret) and a protocol version
  2, which the phone checks; a phone with version 1 keeps working without the new parts.
- The phone's Desktops and Cloud screens merge, and its home screen changes most. Its integration
  tests are rewritten for the new screens.
- Polling costs a little battery while the phone app is open: one small request every 30 seconds
  to Nextcloud, every 5 seconds on the home Wi-Fi.
- Dropbox has to be built again if it is wanted later. The store interface makes that a new file
  per side, not a redesign.

## The owner's choices

Recommended first:

1. **A document sent from the desktop:** the phone asks every time, with "Always accept from this
   computer" in the question; or it always downloads without asking. _Recommended: ask, with the
   "always" option._ Pairing already proves the computer is yours, but a 200 MB download on mobile
   data should not start unasked.
2. **Pairing by QR:** no Accept click on the desktop, because the one-time secret proves the phone
   saw the screen; or keep the Accept click. _Recommended: no click._
3. **Packages:** for the desktop, `qrcode-generator` (MIT, no dependencies, about 60 KB); for the
   phone, `mobile_scanner` (BSD-3, CameraX with the bundled ML Kit model on Android, the system's
   Vision on iOS; it makes no network request). _Recommended: approve both._ Writing a QR
   encoder ourselves is about 400 lines with Reed-Solomon codes, and a scanner is not feasible.
4. **Intervals:** desktop 10 s after a change and every 2 minutes; phone every 30 s with the
   cloud, 5 s on Wi-Fi. _Recommended as written._ Shorter costs battery and Nextcloud requests.
5. **Sync while the phone app is closed** (WorkManager, at most every 15 minutes, one more
   package): now, or later. _Recommended: later._ With the app open, the delays above hold.

## Not verified

- Whether `mobile_scanner` reads a QR code from a laptop screen in poor light. Tried in 7.6.
